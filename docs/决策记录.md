## 声音的 key 为什么不进设置页（2026-11-20 定）

这是刻意的取舍，不是漏做：

- **DSH 自己托管的那把 key 拿不到。** 设置 → 模型里写着「由 Harness 管理」的那把，插件通过
  `ctx.credentials.resolve('DEEPSEEK_API_KEY')` 只读到它的 **ID**（36 位、对应平台上的 Tracking ID），
  不是 secret；拿这个 ID 当 Bearer 去请求 `/v1/tools/tts` 会直接 `401`（本项目实测过）。
- **做输入框就等于把 key 明文落盘。** 设置页要存它，只能写进 `voice.json`（或另做一套记录 + 中转文件），
  两者都会在磁盘上留下明文；而 `voice.json` 还可能被备份、同步、或随手贴进 issue。
- **注意 DSH 凭据库会「压过」环境变量。** 库里已经有一条同名的 `DEEPSEEK_API_KEY`（存的是那把
  App-managed key 的 ID），按 DSH 的规则，存储值优先于启动时的环境变量；插件这里定了自己的优先级：
  **环境变量里的 `sk-…` 优先**，其次是库里的 `sk-…`，库里的 ID 一律忽略（只在日志里说明）。否则
  用户 `setx` 之后仍会被那个 ID 覆盖。
- **别把 Tracking ID 当成 API key。** 开放平台的 key 列表里，`Tracking ID` 和打码的 `Key` 两列挨着，
  而且 key 只在创建时显示一次、之后找不回来。本项目就有一次把 36 位的 Tracking ID 当成 key 存进去，
  结果是每次请求都 `401`，白查半天。复制时认准 `sk-` 前缀；拿不准就先 `curl` 一次再存。
- **所以默认让它留在系统环境变量里。** `setx DEEPSEEK_API_KEY "sk-…"` 写的是 `HKCU\Environment`：
  同样是明文，但**不进插件的配置文件、不进仓库、不进会话记录**，也是这类工具最常见的位置。
- **代价写在明面上**：换 key 要重启 DSH；没设时选这一档不会出声，`status` 的「声音」行与设置页的
  【检查当前选项是否生效】会直接报原因。

`options.apiKey` 作为「不想重启」的后门保留（热读），但文档不推荐它 —— 用不用由你权衡。

## 分叉的定位与纪律（2026-11-15 定）

- **定位：自用脚手架**，服务对象只有一个——黑听抬头机制（只听 + 触发抬眼，含血条读数 P1a–P1c）。不是面向他人分发的产品。这一条不改变上面的「不承诺长期维护」。
- **性质：产品式分叉**，不是补丁式。补丁式是「上游有 bug／缺字段，先垫一下，等合了删掉」；这里是「上游不打算做的能力，自己往外长」。往外长是正当的，但要认账：
  **维护成本 ≈ 差异面积 × 上游变动频率**。上游迭代勤快（4 天 9 版的节奏在 see-on-phone 上已经见过），频率这一项改不了，只能压面积。
- **三条硬条件**（缺一条就不算分叉，算另一个产品）：
  1. **外部契约不动**：工具名、参数名、返回字段、落盘格式跟上游一致；新能力只以「新增」形式出现，不改旧语义。这样上游的 README／issue／release notes 对我们仍然有效——这是待在他下游最大的收益。
  2. **差异集中在扩展区**：上游发新版，merge 进来时冲突只出现在我们自己的文件里。要动他的核心采样链，说明已经不是分叉，得改口径、自己承担采样链的维护。
  3. **单向同步**：上游 → 我们，不往回改（要改就提 issue 或交 patch）。
- **落后检查**：每跟一次上游，跑一次断言集；红了才读 diff，不红直接 merge。判据是断言，不是版本号。

## 发不发的触发条件（2026-11-15 补）

- 现在**不做决定**。决定点不是「用了多久」，而是**「漏抬／误抬能不能给出数」**。
- 自用脚手架的验收面 = **抬头时机**，不是画面准确率也不是 token：
  - **漏抬**：该抬眼时没抬（血条跌破阈值没记、没抬头）
  - **误抬**：不该抬时抬了（画面没变、血条平稳却触发）
  - 标注源现成：血条事件本身就是「值得抬眼」的时刻，一段录屏 + 一条阈值线就能算，不需要人工标注画面。
- 真要发之前必须先做完三件：
  1. **机制可剥离**：触发判定 + preset 独立成层，不渗进采样链（切一刀 vs 重写）；
  2. **一句话说清与上游差什么**（说不清的时候，它已经是事实上的独立产品，只是没做过决定）；
  3. **断言集能跑**（上一条）。
- 分发口径沿用上一节：不发 npm、源码安装、tag + Release 锚点。**「发出去」= 公开 Release 让人装，不等于上 npm。**

## 与上游的关系（2026-11-15）

- **上游采纳优先**。缺字段／语义含糊／声明与实际不符这一类，可以直接要求上游：不需要论证「这个字段重要」，只需要给**最小复现**（例：issue #93 的 108.7s 素材、9 格、12.08s 空档）。
- **判据分两档**：可观测性（缺字段导致模型替它补假设）可以要求上游；**阈值**（空档多少秒算漏、误抬率多少不能发）只能自己定，上游接了反而奇怪。
- 上游不接、而我们现在就要用 → 打**可丢弃补丁**：小到上游合入后能直接删；补丁当提案交回去（issue 里贴 diff + 复现），不当自己的产品。补丁式分叉是筹码，产品式分叉是债务。

## 排布默认不裁画面（2026-11-16，`0.1.1-more.10`）

- **决定**：`pack.solve` 的 `stretch` 默认从 0.3 改成 **0（一格都不裁）**，并做成
  `~/.dsh/see-now.json` 的 `packStretch`（夹在 0–0.3，0.3 = 老行为）。
- **理由**：0.3 不是"拉伸"，是把一行拉成等高带，`coverIntoAt` 按短边铺满、长边居中裁 ——
  最宽格上下各裁 23%、最窄格左右各裁 23%，方向由档位组合决定、**图上不留痕**。
  本机实测（`scripts/pack-crop-curve.mjs`）：快场景 8.66 → 7.72 帧/张（-11%），
  平均裁 8.7% → 0%；**静态场景（全 1 档）两边都是 4.00 帧/张、0% 裁切**。
- **为什么不是纯收益**：不裁之后画布灰条变多（快场景填充 82% → 74%），单格小约 10%，
  小字可读性反而可能下降。所以默认取保守值、把开关交出去，而不是宣布"更清楚"。
- **验收**：`test/pack-stretch.test.mjs` 五条（默认每格正方形、0.3 上限 23%、裁切不丢帧、
  全 1 档不裁、配置越界告警）+ `node --test` 全绿；A/B 图见
  `_scratch/ab-stretch-0.png` / `-03.png`（源画面描洋红边框 + 四角青块，裁掉哪边一眼可见）。
- **对照**：上游 `dsh-see-now` 0.2.4 把默认改成 `maxCrop: 0`，同一口径；我们 0.1.1 基线
  没有 `maxCrop` 预算，用 `stretch` 一个数表达同一件事（0 = 预算 0）。

## 工具契约的体积预算（2026-11-17，`0.1.1-more.15`）

- **决定**：`see_now` 的 description + parameters 有硬预算（`test/tool-spec.test.mjs` 的
  `SPEC_BUDGET_CHARS`）；超了先删长文，再谈加参数。**实测数据、档位推导、像素表进 docs，不进 schema。**
- **理由**：这份文字每一步都在宿主的工具前缀里重发。2026-11-17 量账（宿主的
  `projectToolSchema` 投影，不是自己的估算）：12,103 → 5,738 字符 ≈ 3.9k → 2.0k token；
  345 个会话 / 43,333 步折算，它单独的前缀成本 ≈¥9.4 → ≈¥4.9（命中 0.04、未命中 2.0 元/M）。
- **纪律**：枚举值只从 `ACTION_VALUES` / `PACES` / `SIZES` 取，不手抄；「用了但没声明」的参数由
  单测挡住（`index.js` 读到的每个 `args.X` 必须在 `parameters` 里）；默认值写 `default`，
  不用句子解释。
- **不做**：不给它做 preset 分身、也不为「少装一个工具」搞变体 —— 常驻面 2k token 远低于
  1 万的门槛，不用它的会话占 68% 也没到 80%；省下的钱买不回那份维护。

## 指和等（`pointer`）：三个不动（2026-11-20，`0.1.1-more.23`）

- **不动 `window.py`**：悬浮窗是陪看共用的 489 KB 脚本，`sync-window` 会拿上游覆盖；画圈另起一次性进程
  `examples/floating-chat/pointer.py`（`pick_region.py` 的先例），退出即清屏。这是「差异集中在扩展区」
  那条分叉纪律的直接应用。
- **不用全局热键**：`RegisterHotKey` 抢系统组合键、和输入法冲突；覆盖层鼠标穿透也收不到 Tk 键盘事件。
  改用 50ms 轮询 `GetAsyncKeyState`（左键 / 右键 / Esc）。
- **`change` 不叫 done**：全屏覆盖层下抓屏是冻结画面，像素差判不了；改用 `WindowFromPoint` 句柄变化。
  它只说明「那个坐标上换了窗口」（菜单 / 对话框 / 新窗口），翻页、滚动、视频不算；用户做没做完仍靠 `click`
  或事后看图。
- **默认关**：`~/.dsh/see-now.json` 的 `pointer.enabled`，开发期 `DSH_SEE_POINTER=1`；**不进设置页**
  （设置页在共用的 `window.py` 里）。
- 边界：只支持主屏；D3D 独占全屏下覆盖层不显示（先切窗口化）；同一会话每分钟 ≤6 次。

## 浮窗同步主窗消息与引用（2026-11-26，`0.1.1-more.29`）

- **复用 `chat.jsonl` + `origin:"dsh"`，不另开第二条流**：窗口的显示 / 历史 / 收藏 / 隐藏 /
  删除都只认这一条流；新开流要同步改五处列表逻辑，收藏快照、隐藏 key、删除会话都会分裂。
  代价是四个 JS 消费点各加一道过滤，收成一个 `isFloatUserEntry()`。
- **镜像默认开**：格要的就是「主窗说的话浮窗也看得见」。它是本机展示流的追加，不碰会话、不发消息、
  不联网；`see-now.json` 的 `mirror.users` 是 kill switch。**不放进设置页**（设置页在共用的
  `window.py` 里，越过扩展区）。
- **水位 + `mid` 双保险**：水位保证回填幂等、也保证窗口删掉的条目不复活；启动扫尾部 `mid`
  补「写成功但水位没落盘」的崩溃窗口。只有水位会漏、只有 `mid` 会在超过 4000 行后漏。
- **引用就是 DSH 的纯 Markdown 编码**：`formatQuoteText` 每行 `> `，没有元数据，不改
  `dsh-message-quotes`。浮窗只做同样的编码 + 同样的解析；气泡只对 user 启用，避免顺手改掉
  assistant 的渲染。
- **浮窗 → 主窗显示成用户气泡（2026-11-26 改）**：relay 原来是一条 `source.kind:"see-now"`
  消息，DSH 客户端把它渲染成「收到执行请求」触发卡，用户的话在主窗里不是气泡、引用也不渲染。
  现在拆两条：原话 `source.kind:"user"`，说明另走 `see-now`。副作用是 mirror 会把原话当成
  「用户亲手打的」再镜像回来，所以 relay 的消息 id 落盘（`relay-user-ids.json`），mirror 查表跳过。
  本地图片同理：先存宿主附件库换成 attachment 引用再随原话发（**内联 base64 会把会话打成
  TRANSPORT**，见 CHANGELOG .30）；单张源文件 ≤32MB、最多 4 张，网络图不搬。4MB 的源文件门槛
  是内联时代的旧值（`.35` 改）：DSH 附件库自己归一化到 2048² / ≤4MB，源图准入 50MB。
- **v1 一条引用**：主聊天窗与回顾窗都能引用（`.35` 补了回顾窗：点完关回顾窗、主窗前置）；
  多条引用仍留 P2 —— 要重写单行输入布局。
- 已知边界：~~不回填「窗关着期间的 assistant 正文」~~（`.31` 已补，见下一节）；引用文本里的 `>` 会变成 `> > …`（DSH 剥一层
  后显示原样）；输入法组字期间按退格可能删掉引用而不是删组字，不为此重写输入法状态机。

## 浮窗补齐会话里的模型正文（2026-11-26，`0.1.1-more.31`）

- **关窗也写，不等回填**：回填只在插件启动 / 换绑时跑；如果只在回填里补正文，「关窗聊两句 →
  马上开窗」看到的还是空的。所以 live 直接写，回填只负责插件没起来的那段时间。代价是
  `chat.jsonl` 在窗关着时也长 —— 和 `.29` 的用户消息同一条原则：「回看要完整」优先于
  「没人看就先不写」。
- **assistant 单独一条游标**：用户游标会被后面的 user 推过去，共用会让「正文在它之前、
  当时窗没开」的那批永远补不到。两条游标都只在写成功（或明确跳过）后推进，失败不推。
- **去重分三种**：新条目靠 `mid`；旧 live 条目同文 ±10 秒；`say` 覆盖按「占比 ≥30%、
  ±120 秒」。第一版用「包含即跳过」，实测会把下一轮长回复里顺带提到旧台词的那条吞掉
  （1201 条 assistant 里这类包含对 1 对），加了占比下限。
- **启动补投不认镜像回复**：`pendingStartupEntries` 里 `origin:"dsh"` 的 assistant / meta
  跳过不停。理由：镜像正文回答的是会话里的话，不是「浮窗这句投出去了」。兜底是
  `relay-delivered.json`（200 条）+ 10 分钟 cutoff。
- `mirror.users:false` 的语义随之扩大成「停会话内容同步」（用户消息 + 模型正文），窗里
  `say` 的气泡不受影响。
- 已知边界：不镜像 `reasoning` / `tool-call` / 附件实体；正文 3000 字截断；窗关着时模型的
  回复不朗读（下次开窗也不补念）。

## 主窗发来的图片也进浮窗（2026-11-26，`0.1.1-more.32`）

- **引用附件对象，不复制**：DSH 的 image 块带 `attachmentId:"sha256:<hex>"`，对象文件就在
  `~/.dsh/attachments/v1/objects/<hex 前两位>/<hex>`。直接把这个绝对路径写成 `![图片](…)` ——
  窗口对绝对路径原样加载、按内容解码（不看扩展名）。复制一份进 `see-now/images/` 只会让同一张图
  占两份盘，还得自己管清理。
- **对象不在了就退回 `[图片]`**：附件库可能被清理，或别的存储形态不是 sha256；这时保持 `.31` 的
  `[图片]` 占位，不报错、不重试。
- 这和原来「不搬附件实体」的非目标不冲突：仍然不搬字节，只借路径。
- 已知边界：写进去的是绝对路径，`DSH_HOME` 搬家后老条目会退回 `[图片]`；`assistant` 消息里的图片
  不特殊处理（那是正文 Markdown，本来就按原样显示）。

## 浮窗消息的两处收尾（2026-11-26，`0.1.1-more.33`）

- **纯图不补 `[图片]` 正文**：主窗那侧图片自己就在，多一行占位是噪音，还排在图片上面。
  说明那条仍用 `[图片]` —— 它需要一个「说了什么」的占位，否则文案会变成「引用了一段内容」。
- **插话提示改写**：`.31` 之后正文会镜像进浮窗，「普通回复一个字都看不到」已经不成立；
  只保留「只有 `say` 才会念」。`say` 从硬性要求降成建议 —— 提示卡说错话比少说一句更糟。
- 已知边界：纯图消息在主窗里没有文字，引用 / 搜索都搜不到；要可搜就带一句话。

## 浮窗投递的两处收尾（2026-11-26，`0.1.1-more.34`）

- **说明只在 steer 时投**：两条消息里宿主只 splice 一条，第二条如果走 followup 会被排到
  空闲才拼进会话 —— 用户几分钟后突然收到一张「先说话，再干活」的旧卡片（23:04、23:29、
  23:39 各一次）。反过来，从空闲起的那一轮里用户原话已经起了新回合，`.31` 起正文也会镜像
  进浮窗，这条说明没有额外价值。所以：`steer` 时带 `steer` 立刻投，`followup` 不投。
- **纯图留空改回补 `[图片]`，并让图片排在文字前面**：`.33` 留空是为了不在图上方多一行噪音，
  代价是这条消息在主窗里没有文字，搜索 / 引用都抓不到。`.34` 两头都要 —— 内容顺序改成
  图片在前（和浮窗原文一致），`[图片]` 落在图下方当图注。
- 已知边界：图注就是字面 `[图片]`，不带文件名；按图片内容还是搜不到。

## 浮窗发图门槛与回顾窗引用（2026-11-27，`0.1.1-more.35`）

- **32MB 不是存储上限，是挡板**：插件原来在 `saveImage` 之前按 4MB 拦源文件。查 DSH 的
  `dsh-attachment-local` 才发现归一化是它自己做的——源图准入 50MB、像素上限 6400 万，
  存前缩到 2048² 像素 / 长边 8192 / 目标 4MB。4MB 是内联 base64 时代的保守值（那时要把字节
  塞进内容块），现在走 `saveImage` 传 `Uint8Array`，这个门槛只会把手机照片挡回一行路径。
- **回顾窗引用 = 引用完就回主窗**：回顾窗是独立 Toplevel 且同样 topmost，只设 chip 的话
  输入区被它盖住。选「关回顾窗 + 主窗 lift + 焦点进输入框」，因为引用本来就是为了回主窗发；
  代价是回顾页的滚动位置会丢（重开回到列表页）。
- 不做多 chip 横排：单行 Tk 输入区排多个 chip 要重写布局、命中与删除顺序，收益不值；
  P2 的「多条引用」若做，按「单 chip 存 list、预览显示 ×N」做。
- 已知边界：DSH 对超大像素的图（>6400 万像素）会在 `detectImage` 拒绝，插件照旧退回路径。

## 主窗当前会话：从「扫 Local Storage」改成「Client 推」（2026-11-27，`0.1.1-more.36`）

- **问题**：【关联变更】的预填靠窗口进程扫 Electron 的 Local Storage，而那是**磁盘副本**：
  1. `localStorage.setItem` 同步写内存、Chromium 异步落盘 —— 刚切完会话马上开输入行，
     读到的可能还是上一个；
  2. leveldb 把 `.log` 并成 `.ldb` 时键做前缀压缩，`dsh.sessions.current` 可能只剩
     `s.current`（本机 `000515.ldb` / `000517.ldb` 实测），按完整键名扫描直接返回空。
  两条都让预填「有时候」不对，且都不会报错。
- **决定**：Client 半侧在渲染层读 `localStorage['dsh.sessions.current']`（内存态、即时），
  每 2 秒看一眼、变了才 POST 到 `POST /dsh-see-now-window/current`；Host 落成
  `~/.dsh/see-now/current-session.json`（运行时状态，不进 `see-now.json`）。
  窗口的 `session_hint.py` **先读这份文件**，读不到才退回 leveldb 兜底。
- **leveldb 兜底同时修一个旧 bug**：最新那条键记录是权威 —— 主窗清空选择时值可能是
  `{}`，以前会继续往前翻旧记录、把一个已取消的会话填回来；现在返回空串。
- **开窗即关联**：`POST /dsh-see-now-window/open` 的请求体带上当前会话；Host 先把它写进
  `see-now.json` 的 `session`（会话目录存在才绑，防止旧 id 把窗绑到不存在的会话）再开窗。
  **已经开着的窗**不重启，靠既有 2 秒轮询 `see-now.json` 自己换绑；窗里会落两条关联提示。
- **边界**：同时开两个 GUI（桌面版 + 浏览器）时，两边都会写同一份文件，最后写的算数。
  `dsh.sessions.current` 是 DSH 的内部形状；将来改名时 Client 推不出值，会退回 leveldb
  （同样读不到），届时改 `client.js` 的 `CURRENT_KEY` 与 `session_hint.py` 的 `_KEY`。

## 「折叠气泡」开关（2026-11-27，`0.1.1-more.37`）

- **决定**：折叠态「新消息」预览气泡加一个开关，放【本插件设置】页 —— 「折叠气泡」一行
  （开 / 关，默认开），配置键是 `~/.dsh/see-now.json` 的 `collapsedBubble`。

## 热重载（HMR）在桌面端判不可用（2026-11-27）

目标本来是「改完插件不用重启 DSH」。四条证据说明这条路在这里走不通：

- **它不是 combo bundle**：`@deepseek-ai/dsh-hmr` 的 `package.json` 没有 `dsh.bundle.patch`，写进
  `dsh.profile.bundles` 只会被插件页标红「未运行」（截图确认），不会被组合进树。
- **前置条件其实满足**：它要求 `--expose-internals`（源码里 `if (!this.ctx.loader.internal) throw`），
  而宿主进程本来就是带这个参数起的（`DeepSeek Harness.exe --expose-internals …dsh-desktop-host/lib/index.js`）。
- **默认忽略插件目录**：它的 Config 默认 `ignored: ["**/node_modules", "**/.*", "cache", "data"]`；
  profile 的插件全装在 `node_modules` 下 —— 加载了也永远不看我们的文件。
- **覆盖配置也没救**：改成 patch 插入 + `base/root/ignored` 指向 `node_modules/dsh-see-now-more`
  并重启，改一行文案 + `install-dev` 之后 `status` 仍返回旧文案。四次尝试（bundles ×1、patch 插入 ×1、
  patch+config ×1、重启 ×3）全部失败。

结论：**桌面端 profile 里的插件不靠 HMR 生效**；改插件之后仍需让宿主重新组合，只是这件事应该交给
「自动重启」（`docs/tasks/window-supervisor.md` 的 P1），而不是让人守着窗口。

现状：`cordis.patch.yml` 已回滚到加 hmr 之前（备份 `cordis.patch.yml.bak-2026-11-27T03-09-56-107Z-prehmr`），
`dsh.profile.bundles` 保持 20 条。读宿主内部代码用的抽取脚本在 `_scratch/asar-pick.mjs` / `asar-list.mjs`（不入库）。

## 重启 DSH 由悬浮窗执行（2026-11-27，`0.1.1-more.39`）

目标：改完插件不用人手动关开 DSH。结论：**执行端只能是悬浮窗** —— 它是 `detached: true`
起的（`src/window.js`），宿主重启它还在；而模型和插件都在要重启的那个进程里，重启自己
等于掐掉当前回合。

四条判定（理由也写进了代码注释，这里只留"为什么"）：

- **不走 outbox、不走 `app.relaunch()`**。outbox 是「窗口 → 插件」，可插件就住在要重启的
  进程里，它只能把活转手；`app.relaunch()` 是 Electron 主进程的菜单命令，生产构建里连
  「重启应用与 Host」那一项都没有（`lib/main.js` 只在 development 下加）。
  所以窗口按 `host.json` 的坐标自己 spawn。
- **坐标由插件写**（`src/host-info.js` → `~/.dsh/see-now/host.json`）：`process.execPath` /
  `process.ppid` 只有宿主知道。记录写在**工具注册成功之后**，于是「host.json 是新的」
  就等于「这一次真的起来了、工具注册过了」，窗口的自核不必去翻宿主日志。
- **`ELECTRON_RUN_AS_NODE` 必须剥掉**：Host 是带它起的（本机实测环境里就是 `1`），
  窗口继承着它去 spawn，`DeepSeek Harness.exe` 会当 node 跑 —— 进程在、面板没有。
- **杀进程不用 `/T`**：窗口在 Electron 的进程树上（Electron → Host → 窗口），`/T` 会把
  执行重启的窗口自己一起收掉，于是"关掉旧的、拉起新的"只做一半。按 pid 先杀主进程，
  Host 收 IPC 断开后自己优雅退出，不退再补一刀；`scripts/check-restart.py` 里有一条
  「detached 假窗口必须活下来」的断言守着这条。

两个附带口径：

- **等空闲不设上限**（2026-11-27 真机第一次跑通后改）：`turn-state.json` 里还有 `running` 就
  记成 `waiting-idle` 并等，**不设 15 分钟封顶** —— 回合长度不可预知，封顶会让「点了没成」
  变成常态。等待没有代价（窗口线程不占人），只有「DSH 不在了」或她再点一次才该退出。
  要立刻掐断当前回合就 `host_restart.py --restart --force`。
  代价写清楚：回合没结束时点，重启发生在**这一轮结束之后**，所以回执只能在下一次看到。
- **回执由新宿主写**（`restart.json` 收敛成 `done` + 一条居中提示）：窗口不知道新进程加载的是
  哪一版，它只报"已拉起"。失败则在 `restart.json` 留相位与原因，窗口照实报。

真机第一次跑通（2026-11-27 11:35，`.38` 副本、坐标走窗口标题兜底）：点按钮时那一轮还在跑，
窗口等到回合结束才动手；`restart.json` 记 `oldAppPid 91168`，`restart.log` 记
「Electron 91168: 成功 / spawn pid=94112」，新 Electron 的父进程正是窗口 `92276` ——
**窗口自己没被收掉，跨过了整次重启**。

第二轮（11:42，`.39` 已装进 profile）：新宿主写出 `host.json`（`appPid 94168` / `hostPid 88436`），
`restart.json` 收敛 `done`，回执「已回到 v0.1.1-more.39（窗发起，宿主 ? → 88436，用时 14 秒）」
进了 `chat.jsonl`；新 Electron 的父进程还是窗口（`87424`）。旧宿主记成 `?` 是升级后
第一次的固有形状（那时还没有 `host.json`），不是漏字段。
