## 分发与版本（2026-11-09 定）

**不发 npm。** 用源码安装：`git clone` → `node scripts/install-dev.mjs`（复制进本机 DSH 的 desktop profile，重启生效）→ 以后升级 `git pull` 后再跑一次；卸载 `--remove`。不发的原因：包里带着对 `window.py` 的大改，npm 那套 `prepack` 生成链会把它们冲掉（见「不做什么」）。

**版本锚点靠 tag + GitHub Release，不靠 npm 版本号。** 没有 tag 时：回滚只能翻 commit hash；别人 Watch 仓库勾 Releases、或订 `releases.atom`，全是空的 —— 订阅等于空转。

**版本号写在两处，变更说明写在第三处**，三处必须同值：

| 位置 | 字段 |
|---|---|
| `package.json` | `version` |
| `dsh.plugin.json` | `version` |
| `CHANGELOG.md` | `## [<version>]` 段 |

由 `test/version.test.mjs` 三条守住（含 `name` 一致）。任一不一致 `node --test` 直接红。

**发版五步**：

```
1. 改 package.json 与 dsh.plugin.json 的 version
2. CHANGELOG.md 补一段 ## [<version>]（同一提交）
3. node --test              # 版本/插件名/CHANGELOG 三条守卫会拦漏改
4. git commit && git tag -a v<version> -m "…" && git push origin main v<version>
5. 建 Release：tag 取 v<version>，正文取 CHANGELOG 那段；带 -more.N 后缀的标 prerelease
```

- 带 `-more.N` 的版本在 semver 里是**预发布版**（`0.2.0-more.1 < 0.2.0`），Release 里标 prerelease 才是诚实的信号。
- **`main` 可以领先 tag**：发版之后加的测试、文档、infra 提交不动 tag —— 发布锚点不跟着后续提交漂。
- 第 5 步优先用 `gh release create … --prerelease`（本机 2026-11-10 起有 `gh` 且已登录 `nacivageer`）。
  没有 `gh` 时走 REST API：`POST /repos/nacivageer/dsh-see-now-more/releases`，token 从
  `git credential fill` 取（**不打印**）。

**已发锚点**（全部 prerelease，按时间）：`v0.2.0-more.1` → `v0.1.1-more.3` → `v0.1.1-more.4`
→ `v0.1.1-more.5`（2026-11-10，标题栏入口内置）→ `v0.1.1-more.6`（2026-11-10，上游 0.2.2

## 不做什么

- **不发 npm**（2026-11-09）。上游 `dsh-see-now` 已占住这个名字；本包改名 `-more` 就是为了不撞车。
- **不跑 `npm run sync:window`**。它用上游覆盖 `examples/floating-chat/window.py`，而这里对它的改动很大；`prepack` 生成链已在公开发布准备里去掉了。
- **不承诺长期维护**：够用即停更，上游不自动跟进，本地改动也不保证能合回去。
- **不公开开发期的逐条记录**：CHANGELOG 只从 `0.0.4` 起记，`0.1.1 → 0.2.0` 的主体来自上游。

## 分叉的定位与纪律（2026-11-15 定）

- **定位：自用脚手架**，服务对象只有一个——黑听抬头机制（只听 + 触发抬眼，含血条读数 P1a–P1c）。不是面向他人分发的产品。这一条不改变上面的「不承诺长期维护」。
- **性质：产品式分叉**，不是补丁式。补丁式是「上游有 bug／缺字段，先垫一下，等合了删掉」；这里是「上游不打算做的能力，自己往外长」。往外长是正当的，但要认账：
  **维护成本 ≈ 差异面积 × 上游变动频率**。上游迭代勤快（4 天 9 版的节奏在 see-on-phone 上已经见过），频率这一项改不了，只能压面积。
- **三条硬条件**（缺一条就不算分叉，算另一个产品）：
  1. **外部契约不动**：工具名、参数名、返回字段、落盘格式跟上游一致；新能力只以「新增」形式出现，不改旧语义。这样上游的 README／issue／release notes 对我们仍然有效——这是待在他下游最大的收益。
  2. **差异集中在扩展区**：上游发新版，merge 进来时冲突只出现在我们自己的文件里。要动他的核心采样链，说明已经不是分叉，得改口径、自己承担采样链的维护。
  3. **单向同步**：上游 → 我们，不往回改（要改就提 issue 或交 patch）。
- **落后检查**：每跟一次上游，跑一次断言集；红了才读 diff，不红直接 merge。判据是断言，不是版本号。

## 发不发的触发条件（2026-11-15 补）

- 现在**不做决定**。决定点不是「用了多久」，而是**「漏抬／误抬能不能给出数」**。
- 自用脚手架的验收面 = **抬头时机**，不是画面准确率也不是 token：
  - **漏抬**：该抬眼时没抬（血条跌破阈值没记、没抬头）
  - **误抬**：不该抬时抬了（画面没变、血条平稳却触发）
  - 标注源现成：血条事件本身就是「值得抬眼」的时刻，一段录屏 + 一条阈值线就能算，不需要人工标注画面。
- 真要发之前必须先做完三件：
  1. **机制可剥离**：触发判定 + preset 独立成层，不渗进采样链（切一刀 vs 重写）；
  2. **一句话说清与上游差什么**（说不清的时候，它已经是事实上的独立产品，只是没做过决定）；
  3. **断言集能跑**（上一条）。
- 分发口径沿用上一节：不发 npm、源码安装、tag + Release 锚点。**「发出去」= 公开 Release 让人装，不等于上 npm。**

## 与上游的关系（2026-11-15）

- **上游采纳优先**。缺字段／语义含糊／声明与实际不符这一类，可以直接要求上游：不需要论证「这个字段重要」，只需要给**最小复现**（例：issue #93 的 108.7s 素材、9 格、12.08s 空档）。
- **判据分两档**：可观测性（缺字段导致模型替它补假设）可以要求上游；**阈值**（空档多少秒算漏、误抬率多少不能发）只能自己定，上游接了反而奇怪。
- 上游不接、而我们现在就要用 → 打**可丢弃补丁**：小到上游合入后能直接删；补丁当提案交回去（issue 里贴 diff + 复现），不当自己的产品。补丁式分叉是筹码，产品式分叉是债务。
