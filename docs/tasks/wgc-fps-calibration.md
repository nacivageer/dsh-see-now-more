# WGC 帧率标定（已完成 2026-11-17 12:4x，定 10）

**状态**：可验收 —— `WGC_FPS = 10`（屏幕源仍是 12）。
**结论依据（三组，同一台机、同一窗口）**：

| 跑法 | 实测 |
|---|---|
| 侧车单跑 `--fps 12 --size 798x450` | 12.0 帧/秒（6 秒 72 帧，起手 1.2 秒） |
| 插件里 + 血条同窗口（两个 WGC 会话） | 9.5 帧/秒 |
| 插件里只留画面（血条改抓屏幕） | 10.9 帧/秒 |

取 12 会让 `t = i/fps` 在插件里差 ~8%，所以取 10。

**顺带发现的真问题**：`windows_capture` 每帧都物化一份 8.6MB BGRA 交给 Python，
一个会话就吃近一个核（实测 127–144%），血条那一路 1fps 也占 77–97%。
**后续优化：画面和血条共用同一个 WGC 会话**（现在各起一个 sidecar）—— 那才谈得上回到 12。

**教训**：判断"游戏卡不卡"只能看 **WGC 回调次数**（`--stats` 的 `calls`），
不能看输出帧数（含重复帧，是我们自己的发射频率）。


## 复测方法（以后要再标定就照这个）

1. **窗口真实更新率**：`python py/wgc_capture.py --title "<标题>" --fps 1 --size 798x450 --stats`，
   读 stderr 里 `calls` 的增速（`--fps 1` 让发射几乎不占线程，calls 反映窗口自身更新）。
2. **侧车能不能跟上**：`--fps 12 --size <画布>` 跑 6–8 秒数帧，看是否 ~12 帧/秒。
3. 两者都比对同一时间窗；只跑一个数会分不清"游戏卡"和"侧车慢"。

## 判据（原计划，已用不上但留着）

- 侧车 12fps 实测 ≥11 → 定 12；稳定在 10–11 → 定 10；< 10 → 维持 8 并写明上限。

## 已知背景

- 缩放成本：1922×1126 → 798×450，PIL 的 BOX，`frombytes`+`resize` ≈ 67ms/帧。
- 管线 fps 与 `dtFrames` 必须一起改；只改 fps 会让密度窗变成 1.5 秒。
- 相关：`README.md`「按窗口抓」、`docs/机制.md` 第六节、CHANGELOG `0.1.1-more.15`。
- 提醒：后台窗口的帧率常被游戏自己限到 ~13fps（鸣潮实测），这时测出来的是游戏的限制，
  不是插件能力 —— 要在游戏前台跑。
