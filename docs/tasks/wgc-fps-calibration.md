# WGC 帧率标定（等游戏不卡时做）

**状态**：等条件 —— 鸣潮当时卡得厉害（怀疑官方服务器延迟），测不出侧车上限。
**下一步**：游戏不卡的时候跑一次「两测一判」，然后决定 `WGC_FPS` 留在 8 还是提到 10/12。
**不需要改动代码就能测**（两个命令），只有结论落到 `src/capture-window.js` 的 `WGC_FPS` 才动代码。

## 要测的两个数

1. **源窗口自己更新得多快**（原生抓帧，不缩放）：

   ```
   python py/wgc_capture.py --title "<窗口标题里的一段>" --fps 60
   ```
   头一行是 `{"w":…,"h":…}`，之后每帧 `w*h*4` 字节 BGRA。帧数 / 秒 = **窗口刷新率**。
   这个数字才反映游戏卡不卡；低于 20 说明是游戏/服务器的问题，不是插件。

2. **侧车在目标 fps 下吃不吃得下**：

   ```
   python py/wgc_capture.py --title "<…>" --fps 12 --size 798x450
   ```
   帧数 / 秒 = 侧车实际发射频率。**注意它含重复帧**（窗口没更新时补上一帧），
   所以它不等于游戏帧率，只说明侧车的调度与缩放余量。

## 判据

- 原生帧率 ≥ 30，且侧车 12fps 实测 ≥ 11 → `WGC_FPS` 提到 **12**（同步改 `dtFrames`，
  密度窗 `dtFrames/fps` 必须保持 1 秒）；
- 原生帧率 ≥ 30，但侧车 12fps 实测稳定在 10–11 → `WGC_FPS` 取 **10**；
- 侧车 12fps 掉到 < 10 → 维持 **8**，把「这一路上限 ~10fps」写进
  `docs/机制.md` 第六节，别拿 8 当结论。

## 已知背景（2026-11-17）

- 缩放成本：1922×1126 → 798×450，PIL 的 BOX，实测 frombytes+resize ≈ 67ms/帧 → 理论 ~14fps 上限。
- 当时实测：请求 8fps 输出 7.5fps；同段原生抓帧 7.7fps（游戏自己在卡）。
- 管线 fps 与 `dtFrames` 必须一起改；只改 fps 会让密度窗变成 1.5 秒。
