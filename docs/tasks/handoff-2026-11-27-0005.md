1. **`.31` 浮窗补齐会话里的模型正文**：`mirror.onAssistant` 把绑定会话的 `assistant/message`
   正文（只搬 `text` 块、3000 字截断）写进 `chat.jsonl`，**窗关着也写**；回填用独立游标
   `assistantThroughSeq`（用户游标推走后仍能补）；旧条目按「同文 ≤10s」「`say` 覆盖、占比 ≥30%、
   ≤120s」去重；`pendingStartupEntries` 让镜像 assistant 跳过不停（不遮断启动补投）。
   接线提成可测的 `pushAssistantText()`；朗读仍只在窗开时。
2. **`.32` 主窗图片进浮窗**：`mirrorTextOf(event, env)` 认 `image` 块，按
   `attachmentId = "sha256:<hex>"` 引用 `~/.dsh/attachments/v1/objects/<前两位>/<hex>`，
   写 `![图片](<绝对路径>)`；**不复制**；对象不在 → `[图片]`。窗口按内容解码、不看扩展名。
3. **`.33` relay 收尾（一）**：纯图不再补 `[图片]` 占位；插话提示去掉过时的「普通回复一个字
   都看不到」，`say` 从「必须」放宽成「要念才带」。
4. **`.34` relay 收尾（二）**：说明卡只在 `steer`（原话插进正在跑的一轮）时投、带 `steer` 立刻到；
   `followup`（从空闲起一轮）不投 —— 否则第二条会被宿主排到空闲才 splice，几分钟后变旧卡。
   纯图改回补 `[图片]`，内容顺序改成**图片在前、文字在后**（`.33` 留空导致主窗搜不到）。

## 坑 / 现场（务必看）

- **`attachmentId` 就是 `sha256:<hex>`**，对象文件在 `~/.dsh/attachments/v1/objects/<前两位>/<hex>`；
  窗口对绝对路径原样加载、按内容解码（不看扩展名），所以镜像是**引用不复制**。
- **`chat.jsonl` 的 `origin:"dsh"` 条目**：四个消费点（启动补投 / relay / 常驻循环 / 阻塞 watch）
  靠 `isFloatUserEntry` 挡；新增消费者必须调它。镜像 assistant/meta 在启动补投里「跳过但不停」。
- **steer 与 followup 的排队**：宿主对同一轮里的第二条消息只 splice 一条，第二条会排队到空闲才拼进来。
  所以 relay 的说明卡只在 steer 时投。改 relay 投递顺序前先想这条。
- **测试数字**：`node --test` 现在是 411 / 408；`SPEC_BUDGET_CHARS = 7500` 只剩 24 字余量，
  往 `tool-spec.js` 加字会直接红。
- **`window.py` 是重改版**：不要跑 `npm run sync:window`、不要整文件覆盖。
- **`_scratch/` 不进 git**（`.gitignore`），里面的脚本是这次验证用的，留着可复用：
  `apply_harness.mjs`（装好的插件跑 apply + 发事件）、`check_mirror_live.mjs`、`verify_after_restart.mjs`、
  `real_upgrade_check.mjs`、`dump_session_events.py`（解 zstd 会话日志取事件）。
