## 要什么

- **分档**：3 / 7 / 14 / 30 天，**30 必须留**（格 2026-11-27 12:1x：不是谁都会高频用窗，
  不常用的人几周才翻一次，3 天就把仅有的痕迹删了）
- **默认值**：**30**（护住不常用的人）。格自己会点成 **7** —— 常用、量大的自己收短。
- **UI**：勾选框保留当开关；「超过 N 天」那截点开一个小菜单选档，和设置页「一行点开摊几档」同款
  （不新开交互通道，复用 `_menu_popup`）

## 事实核查：历史里到底记了谁（2026-11-27 12:1x）

格的原判断是「只有被某个会话唤起过才记，所以不会记录 DSH 所有会话」。核了一遍：

- `~/.dsh/see-now/chat.jsonl`：2044 行、**77 个不同 sid**；`~/.dsh/sessions` 下 **86 个**会话目录
- `createSessionMirror`（`src/mirror.js:331`）默认 `users: true`，镜像的是**插件运行期间跑过回合的
  会话**，水位最多记 50 个 sid（`MAX_SIDS`）

所以「不是所有会话」成立（早于插件运行、或从没在插件在线时跑过的会话不在），但**不是**
「只有用过窗的会话才记」。结论不受影响：默认值要看「谁会被默认值伤害」，不是看量。

## 为什么和图库 offload 一起改

- 两件事都在决定「旧的怎么办」：图库是会话里堆的截图（`imageTrigger` / `imageKeep`），
  这里是浮窗历史里的文字记录（`days`）。分开改会出现两个互相打架的口径 ——
  比如图留 100 张但对话记录只留 3 天，回看时图在、话没了。
- 两个都是**窗口/插件两侧各有一半**的旋钮：offload 在插件（宿主侧交付路径），清理在窗口
  （`_run_cleanup`）。同批做才能一次说清默认值与单位。
- 一次改完，文档只需更新一遍（CHANGELOG / README / 本任务书）。

## 边界与风险

- **收藏不受影响**：`favorites.jsonl` 存的是正文快照，清理只删 `chat.jsonl`。
- **删任何记录前先整份备份**到 `trash/`（`_backup_chat("auto")`），恢复路径不变。
- **不碰 `chat.jsonl` 的线格式，不碰 `see-now.json`**：清理只按 `at` 丢行。
- **`session-groups.json` 的 count 会缩水**：历史列表的分组计数要跟着重算，别显示「79 条」但只剩 12 条。
- **插件的投递水位不回滚**：`relay-delivered.json` / mirror 水位记的是「已投递」，清理删行不影响；
  但清理后如果插件又按旧水位回填，会把老消息写回来 —— 需要确认回填的 cut-off 与 `days` 一致。
- 选 3 天时，**只影响「自动」清理**；手动删单条/单组还是原来的确认框（那两张卡的高度刚修过）。

## 验收（待细化，开工前先钉死）

1. 设 3 天，造两条 4 天前 + 一条 1 天前的行 → 只剩 1 天那条；`trash/` 有备份
2. 关掉开关 → 一行都不删
3. 改档不改开关状态；重开窗口后档位还在（`cleanup.json` 持久）
4. 历史列表的分组计数跟着变，不出现「N 条」对不上
