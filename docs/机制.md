# 机制：判据、黑听、听觉、语音与窗口抓

这些是从 README 里搬出来的实现细节。README 留"用户要做的判断"，
这里留"它内部怎么算"——想改参数、想提 issue、想判断某个现象是不是 bug 时看这一份。

## 一、它是怎么判断"变了"的

两条判据，缺一不可。

### ① 切点 —— 这一帧的分数跳得又高又孤立

```
score ≥ cutAbs(12)                 // 绝对地板：变化够不够大
score > 2.5 × max(1, 前后帧)        // 尖峰：是不是"一下子"
mc ≥ cutSpikeMcAbs(20)             // 尖峰也要有 mc 覆盖，防过渡帧先切
距上一刀 ≥ 0.4 秒                   // 不应期

// 补充出口（相机/机位场景）
score ≥ 6 && mc ≥ 60               // 运动补偿：整屏在动但邻域匹配不上 = 换镜头
score ≥ 80 && 跳 ≥ 12 && ≥ 1.5×邻居  // 强台阶：兜住 mc 关掉的配置
6 ≤ score < 12 && score > 3×邻居 && mc ≥ 8 && 包围盒 ≥ 20 && 填充率 ≥ 0.2  // 相似构图：压缩块，不是稀疏 UI 条
```

mc 是运动补偿后的"变了多少格"占比（0–255），搜索半径默认 4 格：
整屏平移 8 格时 radius=2 会误报 194，radius=4 只有 5；换镜头则两边都高。
B 站游戏片里 30.33s 的切机位只有 23.2 分，但 mc=121，靠这条能留下。

前景运动（手、勺子、遮挡物）也会让 mc 变高，所以低/中分切点再加一道**背景模型**：
最近 6 帧里一直没怎么动的格子算稳定背景；如果当前帧只改掉一部分稳定背景
（`bg < cutBgAbs=100`），绝对变化格数不超过 `cutBgMaxChanged=600`，
且变化区域没盖满高度（`mcSpanY < 0.85`），
就按前景运动处理，不切。真正换镜头会把稳定背景整片换掉，或至少盖满画面高度。
宽银幕的上下黑边不计入这个高度（`contentHeightRatio` 归一），否则 Sintel 这类
letterbox 片子的正常切点会被误挡。全黑帧仍按 0 跳过；暗场上下发黑、中间有亮内容时
改用 `guardHeightRatio`，不再因为边缘暗就跳过守卫。

高分候选（`score ≥ 60`）再等 0.5 秒做一次未来帧确认：用最近 24 帧的参考背景
看候选帧改掉的部分有没有回来。手/勺子离开后画面回到旧背景，就不切；真正换镜头
在新场景里稳定下来，仍然切。这项确认只作用于高分候选，低/中分仍走当前帧守卫。

前景停住超过 0.5 秒时，未来帧不会回到旧背景，但外圈通常还是旧背景：
`bgKeep` 之外再看 `bgBorderChanged`，背景变化不到整片且外圈几乎没动时也判前景。
这条只在 `bg < 220` 且外圈 < 10 时生效，避免挡整屏换镜头的真切点。
外圈已经判成前景的候选不再等未来帧；真正的高分切点仍最多等 0.5 秒。

低/中分候选如果**外圈也被改掉**（`border ≥ 60`）、稳定背景很少（`≤ 700`）、
背景变化又不到整片（`bg < 160`），也等 0.5 秒做一次未来帧确认；
只有一部分旧背景回来（`keep < 210`）才判前景。这是在真实带货直播里
大手/产品盖住外圈时补的，静态外框的烹饪/开箱真剪不会被这条带走。

### ② 积分 —— 分不高但一直有，攒够才录一帧

```
need = 4分 × 12fps × 3秒 = 144      // 固定的绝对阈值，不跟着画面一起涨
每帧累加自己的分，累够就录、清零
```

为什么两个都要：**尖峰是相对的**，在低分区也会成立。实测缓慢放大（持续运动）有帧
`s=13.6`、前后邻居只有 1.1/1.3，尖峰判据完全放行 —— 没有绝对地板，它就会被切成一块块。
反过来只有地板也不行：一镜到底的视频每帧 4 分，永远不会"跳"。

## 二、黑听抬头怎么落地

- **警觉**只记账（`lift.jsonl` 一行，不取帧、不叫醒）；
- **瞥**（默认）取「那句话那一刻」的一帧、在窗里落一行（不叫醒）；
- 只有最近 5 分钟里有人跟它说过话（或模型刚回合过），才升级成**看** ——
  叫醒模型，唤醒里带那句话的 `t0`，模型可以 `see_now({action:"lift", since})` 取回那一刻的画面。
  缓冲里滑走了就**明说没了**，不拿当前画面顶；
- 抬头之后 15 秒没人说话、画面也不动，自己回落到警觉。

30 秒精确缓冲是裸 RGB（800×450×3 ≈ 1 MB/帧），10 分钟 ≈ 309 MB 直接加大不现实，
所以另有一条**磁盘低清环**：每 5 秒留一帧、长边 480 的 PNG（10 分钟约 120 帧、
十几 MB），按天分目录。30 秒缓冲滑走后回退到它，取帧结果会标 `degraded:"archive-low-res"`
—— 能看内容、细看不清，不会假装和精确帧一样。

`lift/debug.log` 记诊断账：心跳、扫描计数、叫醒结果，以及**有整句却没命中时那两句的
前 40 字** —— 不写这一行的话，「它怎么没反应」只能靠猜。命中句本来就进 `lift.jsonl`。
两份都只在本机。

## 三、听声音的延迟与调参

**开销**（i9-12900HX，实测）：抓回环 0.3% 单核，转写 3 秒段 130–160ms。
跟画面采集（0.18–0.43 核）比是零头。

**延迟**（"这句话说完" → "模型能读到它"）：

| 环节 | 耗时 | 说明 |
|---|---|---|
| 静音判定 | **350ms** | 要等这么久才确认"说完了" |
| 写盘 + 扫目录 | 5ms + 平均 50ms | `pollMs=100`，Python 是写完 `.tmp` 再 rename，读不到半截 |
| 转写 | 100–180ms | 实测 1.0 秒段 99ms、3.0 秒段 174ms（本地 paraformer，单线程，加并发没用） |
| **合计** | **约 0.6 秒** | 从最后一个字到文字可用 |

**长句不等断句**：连续说话时 `--max-seg`（3 秒）才会强切，这 3 秒里一个字都出不来。
所以现在**说满 1.8 秒就先转一版**（`live-<t0>.wav`，同名覆盖），整句落盘后再覆盖它 ——
真机实测首版字幕从 3.30 秒提前到 **2.08 秒**。临时版在台词里标「还在说…」，
**整句永远盖过快照**（迟到的快照改不回去）。

**还有一段不归 ASR 管**：一张图覆盖 15 秒（`maxWaitSec`），第 3 秒说的话要等第 15 秒出图时
才随图交付 —— 平均 7.5 秒。要更跟得上画面就压 `maxWaitSec` 或用 `pace:"dense"`，
代价是 token 按比例涨。`watch` 返回前还会等最多 300ms（`listener.settle`），
把"差几百毫秒没转完、会被推到下一张"的那句捞回来。

要更快就把 `listen.pollMs` 调小（最低 50，再低只是空转），
或者把 `listen.silence` 从 0.35 再降到 0.25 —— 代价是句子更容易被切成两半。
这些参数都在 `~/.dsh/see-now.json` 的 `listen` 段，改完重开 DSH。

**图上长出了音轨条**：图底下多一条带子（默认档 12px 高），画响度柱、静音灰块和切点刻度 ——
配色和 `dsh-video-storyboard` 一样。数据不用重新解码一遍音频：`listen.py` 断句时已经在算 RMS，
顺手按 0.1 秒一格记下来（`levels.json`），画的时候直接取。条高取的是画面占行后剩下的余量，
不加 token（见下节）。

台词的时间码给两个：`15:57:32 / 9.3s` —— 前面是本机时钟（回头对"当时几点"用），
后面是相对这张图起点的秒数（和每格画面同一个坐标系）。

## 四、token 成本口径

按宿主 DeepSeek-V4 的 patch 网格算：14px patch 向上对齐 → 42px 一格 →
`rows×(cols+1)+2`。

| 档位 | 画布（画面 + 音轨条） | 每张 token |
|---|---|---|
| `low`（默认） | 798×450 + 12px = **798×462** | **222** |
| `standard` | 1050×600 + 30px = 1050×630 | 392 |
| `high` | 1260×720 + 36px = 1260×756 | 560 |
| `ultra` | 1596×900 + 24px = 1596×924 | 860 |

一张图里塞 4 帧还是 8 帧，**价格一样** —— 所以"多留一帧"几乎免费，"漏掉一帧"才贵。

**宽度故意不对齐 16:9，而是对齐 42**（800→798、1066→1050、1280→1260、1600→1596）：
800 会被 pad 到 812 = 19.3 格，白算一整列；798 正好 19 列，面积只少 **0.25%**，
每张省 11~24 token。这是整个链路里唯一**零代价**的降本点（storyboard 那边也是这么干的）。

**音轨条不额外花钱**：token 是按 42px 一行算的阶梯函数，450 高的画面占 11 行、上界 462 ——
底下**空着 12px 也照样收 11 行的钱**。条就用这 12px（其余档位同理：600 余 30、720 余 36、900 余 24）。
所以"加条"和"不加条"的 token 完全一样，关掉它只是图干净一点，省不到钱。

## 五、血条怎么读（`ratioFromPixels` 的 `band` 模式）

口径是**框内血条的填充比例**，不是数 HUD 上的数字。2026-11-16 拍板：主读数永远用条的比例，
数字只当附注 —— 换个游戏，HUD 上不一定印数字（环形条、纯色条、分段条都没有），而填充比例是通用的；
数字读对能佐证，读错不该带偏主读数（真机见过 `2494/17638` 认成 `9/17638`）。

**框哪一条**：自己角色那条**常驻 UI** 的血条。它从进游戏到退出一只在同一位置，框一次就长期有效。
敌人血条只在交战时出现（平时框里什么都没有）、位置随目标跳，框它得到的是忽有忽无的读数，
`gone` 会频繁触发；队友血条同理 —— 位置固定但不是你的血，「低血」的含义完全不同。

坐标不写死任何游戏：用户框一次，之后只读框内。换游戏 / 换 UI 缩放就重新框一次。

**为什么血条优先按窗口抓**：血条这条路走的是 `gdigrab` 抓屏幕像素（region 模式没有 ddagrab 的
偏移参数），所以悬浮窗、浏览器一压到血条上，读到的就是压住它的那块像素 —— 常见后果是每次读数
都在"有血条"和"一片别的颜色"之间跳。配上 `window:"<标题里的一段>"` 就走 WGC 抓窗口自己的表面，
被遮挡照样有；`--region` 收的仍是屏幕物理像素，sidecar 按窗口当前 rect 换算，窗口拖动也不用重框。
代价：窗口**最小化**后停止渲染、WGC 拿不到帧；**D3D 独占全屏**也抓不到（那时该用抓屏幕）。

## 六、按窗口抓（`source:"window"`）

`watch` 那条路也能走 WGC：`source:"window"` + `window:"<标题里的一段>"`。抓的是窗口自己的表面，
窗口被压住、用户切到聊天窗去都不影响 —— 这正是"窗口化游戏 + 时不时切出去"需要的。

**已定的口径（2026-11-17）**：

- **窗口化 / 被遮挡** → 用 WGC；这是它存在的理由。
- **最小化** → **不抓**。窗口停止渲染，WGC 只能等到超时，没有抓的意义；`--check` 探到
  `IsIconic` 就直接报，不建会话。
- **D3D 独占全屏** → **不用 WGC，改抓屏幕**（ddagrab）。WGC 在独占全屏下拿不到表面：会话能建、
  就是一帧都不来。这件事判不出来，所以用**首帧超时**兜底 —— 6 秒没帧就自动切回屏幕抓，
  并在结果里说明"已改抓屏幕"。

**这一路跑多少 fps（2026-11-17 标定：10）**：整窗抓要把窗口原始尺寸（本例 1922×1126 的 BGRA）
缩到画布（798×450），用 PIL 的 BOX（面积平均），`frombytes` + `resize` 约 67ms/帧。
三组实测：

| 跑法 | 实测 |
|---|---|
| 侧车单跑 `--fps 12 --size 798x450` | **12.0 帧/秒**（6 秒 72 帧，起手 1.2 秒） |
| 插件里 + 血条同窗口（两个 WGC 会话） | **9.5 帧/秒** |
| 插件里只留画面（血条改抓屏幕） | **10.9 帧/秒** |

所以管线取 **10**：侧车稳得住，`t = i/fps` 的时间戳不歪；取 12 在插件里会差 ~8%。
`dtFrames` 必须同值（密度窗 `dtFrames / fps`，只改一个会变成 1.5 秒）。

**为什么两个会话就掉下来**：`windows_capture` 每帧都会物化一份 8.6MB 的 BGRA 交给 Python，
两个会话各吃近一个核（实测 127–144% / 77–97% of one core），缩放再叠加。后续优化是
**画面和血条共用同一个 WGC 会话**，那才谈得上回到 12。

**4K 源（2026-11-17 补测）**：游戏全屏时窗口矩形 **= 显示器的物理分辨率**（这里是 3840×2160）。
**别拿逻辑像素当屏大小**：4K 屏开 150% 缩放时，`System.Windows.Forms.Screen.Bounds` 报的是
2560×1440（逻辑），DWM 的窗口矩形与 `--region` 用的是物理像素 —— 拿逻辑值算会以为游戏在超采。
缩放成本随源像素涨，三处优化把吐帧从 ~5fps 拉到 ~9.5fps（插件内实测）：

1. `frombytes` → `frombuffer`（后者不整帧拷贝，4K 上 130ms → 65ms）；
2. 大倍率（≥3×）先最近邻压到 2× 目标再 BOX（181ms → 95ms，亮度均值 69.9 → 70.3，几乎无损）；
3. **不在回调里复制整帧**：33MB × 10 次/秒的 memcpy 会把吐帧压到 ~7fps；改成回调里直接
   裁剪 + 缩放、只把缩好的小图交给发射线程。

**分辨率的影响面**（回答"要不要限到 2K"）：只有**按窗口抓**时缩放成本随窗口像素涨 ——
1080p 窗口 ~67ms（10fps 满速），4K 窗口 95ms（~9.5fps）。血条读的是 421×16 那种小框，
与分辨率无关；字幕带在屏幕源下由 ffmpeg 缩到画布，成本也与屏幕分辨率无关。


**sidecar 的定频发射**：WGC 按窗口刷新率回调（可能 60fps），但下游要固定 fps 的帧流。
所以回调只**登记**最新一帧（限频拷贝），另起一个线程按截止时间每 `1/fps` 秒输出一帧
（窗口没更新就重复上一帧 —— 重复帧的变化分接近 0，正好是"没变"该有的样子）。


`band` 模式四步（都在 `src/bloodbar.js`，纯函数、不吃采集）：

1. **定条带行**：找「左端亮（填充）、框宽 70%–85% 处暗（未填充背景）」的那些行。
   满血白条时右端也亮、左右对比消失，退化成「左端足够亮」；两种判据都不看绝对亮度。
2. **按左端填充色扫填充段**：先用色差粗分，再在填充右侧找一段平坦的列中位色当**未填充背景**，
   然后按「离填充色近还是离背景色近」精分。扫的时候用短窗口中位数，让 2–3 列的中央菱形/
   分段刻度跨得过去，而「一半列白字、一半列暗底」的数字字块过不去。
3. **按背景色定条宽（分母）**：框里常带着右端的 `Lv.90`、括号装饰（真机框 421px、条只有 ~333px），
   拿框宽当分母会把 62% 读成 49%、满血读成 79%。所以从右往左找连续几列接近背景色的那一段，它的右端才是条尾。
4. **兜底**：以上认不出填充时，退回旧的「亮色列占比」法（亮条时它准）。

**框里没有血条就明说没有**：条带内几乎是同一个颜色（过场 / 菜单 / 加载 / 框挪走了）→ 返回
`gone`，不记 0 血、不补判。**覆盖不到**：环形血条、纯数字血量、分段方块血条；
条背景是高饱和色的 HUD 也还没验过。换游戏要先拿真值帧回归 —— `test/fixtures/ratio-samples/`
就是这套回归。

为什么不用「全框亮色占比」（2026-11-14 实测）：框高 36px 里血条只占中间 ~23px，上下是暗边，
全框占比被稀释到 37%；数字又是黑的，再挖掉一块 —— 屏幕上是 90.7%，读数只有 37%。
为什么不再找「最亮行」（2026-11-16）：低血时条变暗红、白字数字比条更亮，最亮行落在数字上，
数字列被当成填充，4.3% 读成 11%、4% 读成 25%。

## 七、念出来之前：语音标记与参数

这是 `say` 从文本到出声的规矩。README 只留「怎么写」，这里留「为什么这么写、参数在哪」。

**先抹 Markdown**：代码块整段换成「（这里有一段代码）」，行内 `code` 去掉反引号，链接只留文字，
标题/列表/引用的前缀去掉 —— 否则 `**加粗**` 会被念成「星号星号……星号星号」（2026-11-20 实报）。

**加粗不进语音**：`**加粗**` 只影响气泡排版。排版的重音和口语的重音标准不同，按 `**` 切词会让接缝
落在词中间、重音落错字（「顺时针」的重音在「顺」，整词切出来就错位）。

**重读用 `〔…〕` 标**（写 `【…】` 也认，两种等价；一条 `say` 只认第一处）：走 edge 自己的 SSML，
一次合成、同一个嗓声：

```xml
<prosody rate='+10%'>你确定？…要一直</prosody><prosody rate='+0%' volume='+15%' pitch='+15Hz'>顺</prosody>，直到…
```

`pitch` 是**合成时**由模型渲染的，不是事后移调，所以不会换嗓声（事后移调谱包络差 0.044）。
服务端最多认 **2 段** `<prosody>`，第 3 段直接 `NoAudioReceived`，所以重读只能是一段连续文本，
前后两侧不能同时单独调速。

**`‖` = 换气口**，不是逗号：先把 `‖` 换成逗号让引擎自己吐气、**一次合成**，再把内部静音压到
200ms —— 切段合成会让后半句带句尾下落和新的起音，就没有「弹簧按一下又弹回来」的连贯感了。
这条裁剪作用于**全句内部所有静音**，句子里本来就有的逗号也会被压到同一长度。

**`~` = 拖音**：去掉波浪号、整句放慢（默认 `-22%`，每多一个再 `-8%`，封顶 `-45%`）。注意是
**整句一起慢**——所以「慢」在 edge 上会读成撒娇，读不成害怕（害怕要气声与颤抖，那是音色层的事）。

**表演提示不念**：`呃啊！（发抖）太吓人了！` 里的「（发抖）」先剔掉。判据三条同时满足：括号里
≤8 个字符、不含数字/拉丁字母/句内标点、且贴着句子边界（前面是开头或 `！？。，…；、` 空白，或
后面是结尾/这类标点）。`看这个（第二阶段）的弱点` 这种前后都是字的真内容不会被误删。

**情绪前缀**（写在一条 `say` 的开头，只影响这一条）：

| 前缀 | 映射 | 用在哪 |
|---|---|---|
| `【急】` | 语速 `+15%`；带重读段时音量：重读段 `+25%`、前缀 `+10%`（后缀走默认） | 「哇，小心！」「是小昆！」这种；三声的下沉会被语速自然压平 |
| `【柔】` | 语速 `-8%`；带重读段时音量：重读段 `-15%`、前缀 `-10%`（后缀走默认） | 「唉，没事的。」这种 |

音量那半**只在同一句里有 `〔…〕` / `【…】` 时生效**：没有重读段时整句走一次普通合成，只改语速。
后缀不套 prosody 是 edge 那 2 段的限制（见上），不是漏配。

**一句只合成一次**：除了 `‖` 那口靠内部静音裁剪，整条 `say` 是一次合成，所以没有接缝，也不会
出现「一句话被几个人接力读完」。代价是只能标**一段**重读，不能逐词各调各的。

**参数**：`~/.dsh/voice.json` 的 `options.emphasis`（热读）。最常用的三个：`baseRate`（非重读段
语速，默认 `+10%`）、`baseVolume`（非重读段音量，默认 `+0%`）、`breathMs`（换气口，默认 200）。
其余（`rate` / `volume` / `strongPitch` 等）见 `examples/voice-edge-tts.mjs` 顶部。

**标记由适配器各自渲染**：edge-tts 全支持；SAPI 支持 `〔…〕` / `【…】`、`‖`、`~` 和情绪前缀的
语速（没有音量那半）；DeepSeek 的合成接口不收标记，送出去前会先剥掉（重读 / 换气 / 拖音不生效，
只剩正文）。

**边界**：字级重读（「第二~阶段」那种只拖一个字）和音素层（「xin」里 i 尖、n 弱）edge 都不暴露
——按词的切分试过能量谷 / 音节核 / 谱通量三种检测，四字词上都不稳；真要做得换引擎（SAPI 的
SSML 或带 style 的云 TTS）。

**适配器自己的两件事**：串行（两个 `say` 抢音频设备会像结巴）和 `spoken` 上报（出声那一瞬发，
不能等念完 —— 展示层是"字跟着声音走"的）。

## 八、指和等（`pointer`）

`action:"pointer"` 是唯一会往用户屏幕上画东西的动作：指一个坐标，停住等一个信号，再把「等到的是哪种」
如实报出来。一次一个圈，进程退出即清屏，没有常驻覆盖层。

### 为什么不碰 `window.py`

悬浮窗那颗 489 KB 的共用脚本（陪看项目也在用，`sync-window` 会拿上游覆盖）不适合为「画一个圈」启动一整套生命周期。
画圈放在 `examples/floating-chat/pointer.py`，和 `pick_region.py` 同一位置 —— `sync-window` 不碰这两个文件。
Node 侧是 `src/pointer.js`：开关、参数校验、挑解释器、超时；Python 只负责画与等，stdout 吐一行 JSON。

参数走**环境变量 `DSH_POINTER_ARGS`**（JSON），不走命令行：中文 `label` 在 Windows 命令行引号里很容易被拆坏。

### 为什么不用全局热键

`RegisterHotKey` 会抢占系统组合键、和输入法打架；覆盖层又是鼠标穿透 + 不可聚焦的，Tk 收不到键盘事件。
改用 `GetAsyncKeyState` 每 50ms 轮询左键 / 右键 / Esc：不抢键、不需要管理员；鼠标穿透只影响窗口收不收消息，
不影响全局轮询。

### `change` 为什么不是像素差

最初的判据是「半径内画面变化 ≥3% 且随后稳定」。实测失败：**覆盖层铺满最上层时，抓屏拿到的是冻结画面**
（同进程 `mss` diff 恒 0，换子进程也一样），像素差这条路根本不成立。
现在每 200ms 问一次 `WindowFromPoint(x,y)`：那个坐标上的窗口句柄变了，就是「那儿换了窗口」。
语义因此收窄 —— 菜单、对话框、新窗口开在那儿会触发，翻页、滚动、视频内容变化不会。
它叫 `change` 不叫 `done`：只说明「那儿出现了别的窗口」，不说明用户做对了。判断「做完了」仍要靠 `click`，
或事后 `watch` 看一眼结果。

### DPI 与坐标口径

本机 150% 缩放。不声明 DPI aware 的 Tk 窗口，`geometry('+300+300')` 会落到 450,450，尺寸也放大 1.5 倍。
`pointer.py` 在**建窗之前**调 `SetProcessDpiAwareness(2)`（失败退 `SetProcessDPIAware`），之后
`GetSystemMetrics` / `GetCursorPos` / Tk 坐标统一是物理像素，与 `region` 同口径。

### 定时链不能断

`tick()` 靠 `root.after(50, ...)` 自己续拍；任何提前 `return` 都必须走 `try/finally` 续拍。
断一次 `mainloop` 就会空转、窗口永远挂在屏幕上，只能去 kill 进程（开发时定基线那一帧踩过）。
退出统一走 `finish()`：emit 一行 JSON → `root.destroy()`；Node 侧另有 `waitMs + 5s` 的超时兜底。

### 额度与返回

- 坐标只收主屏内的非负整数，越界拒绝、不画；
- `label` 必填（不许画空白圈），超过 40 字截断并回 `truncated:true`；
- `waitMs` 夹在 1000–120000（默认 20000），`radius` 夹在 20–400（默认 60）；
- 同一会话每分钟最多 6 次（内存计数），防连续指路刷屏；
- 信号六种：`click` / `change` / `timeout` / `none` / `cancelled` / `unknown`；Esc / 右键走
  `ok:false, reason:"cancelled"`，与 `region` 的取消约定一致；
- 子进程崩了、没有 JSON → `unknown`，不重画、不重试。

## 九、原生截块（`crop`）

`action:"crop"` 只抓 `region` 那一块，一根 PNG 管道出来，**不缩放、不拼图、不落盘**。
它是给「读小字 / 认图标 / 定位后再画圈」用的：整屏 `watch` 在 4K 上会缩到 1260 宽，
桌面图标和 10px 的字在那种尺寸下读不出来。

### 为什么直接走 ffmpeg 的 gdigrab

`watch` 那条采集管线会把帧缩到画布（档位长边），再打分、拼图——这是为「看变化」设计的，
不是为「读一块的每个像素」。`crop` 绕开整条管线，只让 ffmpeg 抓一块：

```
ffmpeg -f gdigrab -offset_x X -offset_y Y -video_size WxH -framerate 5 -i desktop \
       -frames:v 1 -f image2pipe -vcodec png -
```

`-offset_x / -offset_y / -video_size` 正好就是块坐标，和 `region` 走的是同一条 gdigrab 路径，
不新增 Python 依赖（血条抓屏也用它）。代价是 GDI 抓屏比 ddagrab 慢一点，但只抓一帧、一块，
实测几百毫秒；要连续看画面仍然用 `watch`。

### 坐标与成本

- 坐标与 `region` / `pointer` 同口径：**主屏物理像素**；块内 `(u,v)` = 屏幕 `(x+u, y+v)`，
  所以 crop 完直接就能算 `pointer` 的 x/y。
- 一样按 42px 一格计 token：300×400 ≈ 90 token，2000×1100 ≈ 1.3k token；面积上限 220 万像素，
  再大就该用 `watch` 看整屏。
- 不改 `region.json`：它是一次性取景，不是「以后都只看这块」。
- `watch` 与 `crop` 的分工：`watch` 回答「这段时间发生了什么」，返回队列里攒下的 sheet
  （可能晚几十秒）；要「现在是什么」用 `crop`，它绕开队列直接抓当前像素。拿 `watch` 当现状基准，
  在两图对照时会拿错帧。

## 十、浮窗消息镜像与气泡引用（2026-11-26）

### 消息镜像：同一条 `chat.jsonl`，靠 `origin` 分流

浮窗的气泡流只有一个来源 `~/.dsh/see-now/chat.jsonl`。用户在主窗说的话本来只在会话日志里，
于是浮窗回看只有 assistant 半边。镜像**没有**另开第二条流，而是往同一个文件追加
`origin:"dsh"` 的条目，理由是新开流要同步改窗口的显示 / 历史 / 收藏 / 隐藏 / 删除五处，
而且收藏快照、隐藏 key 都会分裂。

这条流有四个消费者把 `role:"user"` 当成「用户刚在浮窗说话」：

| 消费者 | 漏过滤的后果 |
|---|---|
| 启动补投 `pendingStartupEntries()` | 重启后把历史自己讲的话再投一遍 |
| relay 增量 `chatWatcherShared()` | 同上（每 700ms 一拍） |
| 常驻循环 `loop.js` | 把历史当成插话，叫醒一次 |
| 阻塞 watch `runner.js` | 截断当前出图，误以为用户插话 |

所以判断只写一份：`chat.js` 的 `isFloatUserEntry(entry)`（`role === "user" && origin !== "dsh"`），
四处都调它。**以后新增第五个消费者也必须调这个函数**，不要各写一份。

### 去重与水位（两个都要）

- `mid = "<sid>:<seq>"` 写进条目，实时与回填共用；启动时扫 `chat.jsonl` 尾部 4000 行已有的
  `mid`，补「写成功但水位没落盘」的崩溃窗口。
- 水位在 `~/.dsh/see-now/session-mirror.json`：`{v:1, sids:{sid:{throughSeq, updated}}}`，
  最多 50 个会话。**`appendChat` 成功才推进**；写失败不推，下次重试。
- 水位还负责「用户在浮窗里删掉 / 隐藏的条目不被回填复活」——窗口删的是 `chat.jsonl` 条目，
  水位在另一个文件里，不受影响。
- 回填：`sessionQuery.readSession(sid)` → 跳过 `inheritedEventCount` 之前的 fork 继承前缀
  → 只取 `user/message` + `source.kind === "user"` + `seq > 水位` + 30 天内 → 取最近 500 条
  → 按 seq 顺序写。扫完没有可写的也要把水位推到最后一条 seq，避免每次重扫。

### 引用：协议就是「每行 `> `」，没有元数据

DSH 主窗的引用由 `@deepseek-ai/dsh-message-quotes` 实现，编码是纯 Markdown：
`formatQuoteText(text)` = 统一 CRLF → 按 `\n` 切 → 每行前缀 `> ` → 拼回。没有引用 id、
没有额外字段；模型看到的和主窗看到的是同一份文本。所以浮窗只要照这个编码，
主窗和模型都认，不需要改 DSH。

浮窗自己的气泡也要认同一套 `>` 行，否则发出去的话在浮窗里显示成裸 `>`。解析规则与 DSH 的
`quoteRule` 一致：连续的、最多 3 个前导空格的 `>` 行，剥掉一个 `>` 和它后面一个空格；
遇到第一条非引用行结束；整块去空白后为空则丢弃。**只对 user 气泡启用**，assistant 正文里的
`>` 维持原样。

输入区是单行隐藏 Entry，做不到 DSH 那种原位原子节点，所以 chip 固定在正文左侧：
开引号 + 单行预览（换行 / 连续空白压成空格）+ 闭引号 + ×；点 × 或光标在正文开头按退格 /
Delete 删除。发送拼装 = `引用块 + "\n\n" + 展开后的正文`（只有引用时就是引用块）。

### relay 的包裹

浮窗消息交给模型时拆成两条（2026-11-26 改）：

1. **用户原话**：`source.kind:"user"`，逐字不动（引用块、图片 Markdown 都在）。DSH 客户端
   把它当普通用户消息 —— 主窗显示成用户气泡、引用按 Markdown 渲染。
2. **说明**：`source.kind:"see-now"`，内容是 `[看屏幕·用户插话] 「正文」` + 「先说话再干活」。
   它仍会以「收到执行请求」触发卡的形式出现在主窗，但只有这段说明进卡，用户的泡泡是干净的。

为什么必须拆：DSH 客户端把非 `user` 来源的消息渲染成 **turn-trigger 卡**（自动化任务 /
收到执行请求），不是聊天气泡 —— 一条 `see-now` 消息会让用户的话在主窗里根本不像自己说的，
引用也不会走 Markdown 渲染器。

**回灌过滤**：原话用的是 `source.kind:"user"`，mirror 会把「source.kind=user」当成用户亲手
打的字再镜像回浮窗。relay 生成的消息 id 落在 `~/.dsh/see-now/relay-user-ids.json`（最近 200 条），
mirror 的 live 与回填都查这张表跳过。id 落盘是为了重启后回填也不重复。

引用条仍按 DSH 的 `formatQuoteText` 编码（每行 `> `），说明里的正文仍截 200；原话那条不截断。
待回执（`noteInterjected`）只记正文，避免「你还没回」复读四千字。

**本地图片**：浮窗粘贴图片写进正文的是 `![图片](本地路径)`，主窗不解析本地路径 Markdown。
relay 投递前把本地图拆出来，读成 `{type:"image", data:base64, mimeType}` 内容块随用户消息发；
单张 ≤4MB、最多 4 张，超限 / 读不到 / 格式不认识的**保留原 markdown**（模型还能沿路径读）。
网络图（`http(s)`）不搬。
