# 重造账

> 这份仓里哪些是借来的、哪些是自己写的、哪些是自己造完又没在用的。
> 用途只有一个：以后要决定「砍不砍玻璃」「拆不拆窗」时先看这一页，别重新数一遍。
> 盘点日期 2026-11-21（session-e8ce190b）；口径与复核命令见文末。

## 结论

- **没有自研引擎。** 采屏是 ffmpeg，音频是 pyaudiowpatch，ASR 是 sherpa-onnx（或外部兼容服务），OCR 是 Windows.Media.Ocr。四处都是借的，而且每处都在代码里写了「为什么不是别的」。
- **自写且必要**：门控 / 节奏 / 拼图 ≈4.9k 行、黑听自写部分 ≈1.6k、lift 1,421、coverage 402、血条 677、指针 381、工具面 2,329。这些是产品差异本身，拿不到现成的。
- **白造**：玻璃四件套 1,088 行（默认不走、代码仍活）、早期 dxcam 一段（已撤，只留经验）。合计不到全仓的 4%。
- **最大单块是窗**：`window.py` 9,277 行（上游 0.1.1 是 1,163）。形态必要，实现成本最高，也是唯一「越维护越贵」的部分。

## 口径

- 行数 = 物理行（含注释与空行），`Measure-Object -Line` 数出来的。
- 范围 = 本仓 `src/` `py/` `examples/` `scripts/` `bin/` `client.js`；**不含** `test/`、`_scratch/`、`.tmp/`、`node_modules`。
- 上游基线 = `_scratch/upstream-v011`（上游 `dsh-see-now` 0.1.1，Apache-2.0，见 `NOTICE` 与 `LOCAL-CHANGES.md`）。
- 本仓是**发布线**；开发线是另一个仓 `see-now/`（同为本地存档线，不从上游 merge）。两边不要混着数。
- 统计时点版本：`0.1.1-more.25`。

## 三处白造

### 1. 玻璃四件套（1,088 行，默认不走但代码仍活）

`glass_capture` 268 + `glass_cpu` 132 + `glass_geometry` 250 + `glass_gpu` 438，同一个 `render(source, sct, bbox)` 接口两条实现（CPU / GPU moderator+OpenGL）。另有兼容层 `glass_window.py` 7 行、`glass_window_gpu.py` 13 行。

现状要说准确：

- 主窗**默认走纯色深面板**（`window.py` 里 `self._plain = True`），`_plain_frame()` 是默认渲染路径。
- 但玻璃路径**没有删**：`from glass_cpu import CpuRenderer` 仍在，`USE_GPU` / `NATIVE` / `DSH_GLASS_PLATE` 三个环境变量仍能切回去，`_plain` 分支在窗里出现 15 处、`PLATE` 出现 12 处。

所以这块不是「已淘汰」，是「非默认但保留」。保留的价值只有一条：拍新旧对比截图和偶尔看玻璃效果。成本是一千多行的维护面 + 三个环境变量的语义。

**要砍的话**先确认两件事：`DSH_GLASS_PLATE=0` 的对比截图还有人看吗；`DSH_GLASS_GPU/NATIVE` 是否有人真在用。

### 2. dxcam 那一段（已结清）

`LOCAL-CHANGES.md` 第 61 条曾把抓屏换成 dxcam（DXGI Desktop Duplication 的 Python 绑定），第 62 条随即踩到「自捕获导致画面叠加」，后来整条回到 ffmpeg 的 `ddagrab`。代码没留下，留下的是一张三源实测表（见 `src/capture.js` 文件头）：`ddagrab` 0.28 核 / `gdigrab` 0.45 核 / `obs` 0.13 核，首帧分别 370 / 310 / 575 ms。这张表是这笔学费唯一的产出。

### 3. 上游快照与窗备份（不是功能轮子，是维护轮子）

`_scratch/` 里躺着四份上游快照（`up-watch-together` / `upstream-20261110` / `upstream-v011` / `up-024`），`.tmp/` 里还有两份 `window.py` 备份（7,930 / 9,010 行）。它们不进 git，但占磁盘、也让「哪份是真的」每次都要判断。**要清就整目录清**，别留半份。

## 窗这笔账（拆不拆）

`window.py` 从 1,163 长到 9,277 行，是全仓最大的自加项，也是 `LOCAL-CHANGES.md` 八十多条里绝大多数条目的主体（气泡高度、拖动掉帧、黑条、标题栏残留、缩放重排……）。

它不是轮子：常驻、置顶、可插话、不进聊天主流程，这四条官方没有可复用的东西，第三方 `dsh-subtitle-pointer` 分发不可得（已排除）。

它是**形态必要、实现方式可疑**：9.3k 行 Python 自绘 IM，换成 DSH client plugin 的 web 面能不能做到七成？侧栏与弹层能，置顶悬浮不能。所以当时选这条路没错。

什么时候该重新算这笔账，看三个判据：

1. 窗的改动是否还集中在「像素级修复」而不是功能。若是，说明自绘 UI 的固定成本还没摊完。
2. DSH 是否出现官方的常驻浮层 / 桌面层能力。出现就该重估。
3. 是否出现第二个需要这套窗的插件。出现就该把窗抽成独立包，而不是继续在插件里长。

## 借得对的证据

「不重复造轮子」的正确形态是借，并且把**为什么借这个**写进代码。本仓三处都做了：

- `src/capture.js` 文件头：三源实测表（首帧 / CPU 核数）+ macOS 两条坑（`-framerate` 不压速、无录屏权限静默给黑帧）。
- `py/listen.py` 文件头：`soundcard` 的 loopback 四个端点恒返回 0、`sounddevice` 的 WASAPI host API 根本不列 loopback、只有 `pyaudiowpatch` 打补丁暴露；另记 WASAPI loopback 静音时不推送数据。
- `src/index.js`：明说插件里没有 OCR 引擎，字幕带用边沿密度近似（并给出对 OCR 真值的成绩）。

## 边界与未核

- **没有通读 2.9 万行。** 依据是：文件规模、约十五个文件的头部注释、`LOCAL-CHANGES.md` 的目录、`docs/决策记录.md`。所以误差在「某块算不算必要」的边界，不在总量。
- 只比了上游 0.1.1。上游之后是否又发了版本、有没有可以反向拿的东西，没比。
- 行数不区分有效代码与注释；本仓注释密度很高（文件头大段写「为什么」），按行数读会高估实现量。
- 工具面（`index.js` 1,925）只看了规模与工具清单，没审每个工具的 schema 成本。

## 怎么复核

```powershell
$m = 'C:\Users\Administrator\Documents\deepseek-harness\see-now-more'
# 总量（排除 test/_scratch/.tmp/.git）
$files = Get-ChildItem $m -Recurse -File -Include *.js,*.mjs,*.py |
  Where-Object { $_.FullName -notmatch '\\(test|_scratch|\.tmp|\.git|node_modules)\\' }
$js = 0; $py = 0
foreach ($f in $files) {
  $n = (Get-Content $f.FullName | Measure-Object -Line).Lines
  if ($f.Extension -eq '.py') { $py += $n } else { $js += $n }
}
"js+mjs: $js"; "py: $py"; "files: $($files.Count)"
```

分区行数按文件名逐个取即可（`window.py`、`src/lift/*.js`、`glass_*.py`、`bloodbar*.js`）。上游基线在 `_scratch/upstream-v011/src` 与 `_scratch/upstream-v011/examples/floating-chat/window.py`。
